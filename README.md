# Система Управління Бібліотекою

Клієнтський застосунок для обліку книг і користувачів бібліотеки з позичанням та поверненням книг.
Лабораторна робота №2. Весь інтерфейс генерується з TypeScript-коду, в `index.html` лише `<div id="app"></div>`.

**Демо:** https://anna-adelina.github.io/library-app/

## Можливості

- додавання книг і користувачів із валідацією (обов'язкові поля, рік за регулярним виразом);
- позичання та повернення книг, не більше 3 книг на одного користувача;
- повідомлення й підтвердження через модальні вікна Bootstrap (без `alert`);
- пошук книг за назвою або автором;
- пагінація списків (5 елементів на сторінку);
- видалення книг і користувачів (позичену книгу або користувача з невернутими книгами видалити не можна);
- збереження даних у LocalStorage.

## Технології

TypeScript (класи, інтерфейси, generics, модулі, namespace), Bootstrap 5, Vite, Mocha + Chai, ESLint + Prettier, Husky.

## Запуск

```bash
npm install
npm start          # dev-сервер на http://localhost:9000
```

| Команда           | Що робить                                   |
| ----------------- | ------------------------------------------- |
| `npm start`       | dev-сервер                                  |
| `npm run build`   | перевірка типів і продакшн-збірка в `dist/` |
| `npm run preview` | локальний перегляд збірки                   |
| `npm test`        | юніт-тести (Mocha)                          |
| `npm run lint`    | ESLint                                      |
| `npm run format`  | Prettier                                    |
| `npm run deploy`  | збірка й публікація в гілку `gh-pages`      |

## Архітектура

Код розділено за шарами відповідальності:

```
src/
├── models/      # Book, User та інтерфейси IBook, IUser (тільки дані)
├── services/    # Library<T>, Storage, BorrowService, RemovalService, NotificationService
├── utils/       # namespace Validation, пошук, пагінація, генератор id
├── ui/          # компоненти й DOM-логіка
├── types/       # спільні типи
└── index.ts     # точка входу
tests/           # тести Library, Validation, пагінації, пошуку, видалення
```

- `models` нічого не знають про UI чи LocalStorage;
- `services` містять бізнес-логіку й не торкаються DOM;
- `ui` єдиний шар, що працює з DOM.

## Процес розробки

- Feature branch workflow: кожна функція в окремій гілці, зливання через pull request.
- Conventional Commits (`feat:`, `chore:`, `test:`, `build:` тощо).
- Husky pre-commit: перед кожним комітом автоматично запускаються ESLint і тести Mocha, і коміт блокується, якщо вони не пройшли.
- Замість `.eslintrc` використано `eslint.config.mjs`: ESLint 10 більше не читає старий формат `.eslintrc`.

## Порівняння webpack та Vite

Спочатку проєкт зібрано на webpack (остання webpack-версія: коміт `185c0f9` у `main`), потім у гілці `vite-migration` він перенесений на Vite. Застосунок працює однаково, змінилась лише збірка.

### Висновок

**Швидкість.** Vite виявився помітно швидшим у всіх вимірах: dev-сервер стартує приблизно в 5 разів швидше, а продакшн-збірка за внутрішнім часом приблизно в 10 разів швидша. Причина в підході: під час розробки Vite віддає браузеру модулі як є й лише перетворює TypeScript, а webpack спершу збирає весь код у один файл.

**Конфігурація.** Для webpack довелось встановити й налаштувати сім пакетів (`webpack`, `webpack-cli`, `webpack-dev-server`, `ts-loader`, `html-webpack-plugin`, `css-loader`, `style-loader`) і написати 26 рядків конфігу з правилами для кожного типу файлів. У Vite потрібен один пакет і 11 рядків: TypeScript, CSS і HTML він обробляє з коробки.

**Розмір збірки.** Загальний розмір майже однаковий, бо основну вагу (230 КБ) дає Bootstrap CSS. Різниця в структурі: webpack вбудував CSS у `bundle.js` (через `style-loader`), а Vite виніс його в окремий файл, тож стилі й скрипти вантажаться паралельно й кешуються окремо. Webpack при цьому видав попередження про перевищення рекомендованого розміру, Vite ні.

**Підключення UI-фреймворку й TypeScript.** Bootstrap у Vite підключається одним `import` без жодних лоадерів. Проте є нюанси: Vite лише прибирає типи й **не перевіряє їх**, тому команду `tsc --noEmit` довелось додати в скрипт `build` вручну (у webpack це робив `ts-loader`). Також у `index.html` довелось додати `<script type="module">` для точки входу, а `html-webpack-plugin` робив це автоматично. Ще Vite 8 показує безпечне попередження про ESM-синтаксис у `vite.config.ts` (у `package.json` немає `"type": "module"`).

**Екосистема.** У webpack більше готових лоадерів і плагінів та більше історичних прикладів у мережі, що корисно для складних проєктів. Для невеликого SPA більшість цих можливостей не знадобилась.

**Суб'єктивна оцінка.** Для невеликих SPA-проєктів на кшталт цього Vite зручніший: менше залежностей, коротший конфіг, майже миттєвий запуск. Webpack доцільно обирати там, де потрібне складне тонке налаштування збірки. Для цього проєкту я б обрала Vite.

## Деплой

Збірка публікується на GitHub Pages командою `npm run deploy` (гілка `gh-pages`). У `vite.config.ts` для продакшн-збірки задано `base: "/library-app/"`, бо сайт лежить у підпапці домену.
